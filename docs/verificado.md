## LangGraph and the Postgres checkpointer

- `langgraph` 1.2.22 and `langgraph-checkpoint-postgres` 3.2.1, both released 2026-11-14, Python 3.10 or newer. (https://pypi.org/project/langgraph/, https://pypi.org/project/langgraph-checkpoint-postgres/)
- The checkpointer uses psycopg 3, not asyncpg. A connection passed by hand must have `autocommit=True` and `row_factory=dict_row`. It accepts an `AsyncConnectionPool`. `setup()` creates `checkpoint_migrations`, `checkpoints`, `checkpoint_blobs` and `checkpoint_writes`. (https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint-postgres/README.md and the package source)
- Old threads are removed with `adelete_thread` or `aprune`. There is no TTL; the docs suggest a scheduled job. (https://docs.langchain.com/oss/python/langgraph/persistence)
- On resume after an interrupt "the runtime restarts the entire node from the beginning", so code before `interrupt` runs again. The docs advise idempotent side effects and separate nodes for them. Resume is `Command(resume=...)` on the same thread id. An interrupt "waits indefinitely". (https://docs.langchain.com/oss/python/langgraph/interrupts)
- The default step limit is 10,007 super-steps since 1.1.4, overridden with `recursion_limit` as a top-level config key; exceeding it raises `GraphRecursionError`. (https://docs.langchain.com/oss/python/langgraph/graph-api)
- Durability is `exit`, `async` or `sync` per execution. `sync` persists the checkpoint before the next step starts; `async` carries a small risk of a missing checkpoint on a crash. (https://docs.langchain.com/oss/python/langgraph/checkpointers#durability-modes)
- State can be a `TypedDict`, a dataclass or a Pydantic model. With Pydantic, runtime validation happens only on the input to the first node. (https://docs.langchain.com/oss/python/langgraph/graph-api-state)

- Observed by running `langgraph` 1.2.22 with `langgraph-checkpoint-postgres` 3.2.1 on 2026-11-18 (backend/tests/worker/test_approval.py). A node that calls `interrupt` stops the run and `ainvoke` returns the state with the pending value under `__interrupt__`. `Command(resume=...)` on the same thread id, through a different `AsyncPostgresSaver` object on the same database, continues from that node, and the node runs again from its first line. With `durability="exit"` the checkpoint of the interrupted run is there to resume from. `JsonPlusSerializer(allowed_msgpack_modules=[...])` given this project's dataclasses and Pydantic models round-trips them; without a list the library accepts unregistered types with a warning unless `LANGGRAPH_STRICT_MSGPACK` is set. `setup()` creates the four tables for whichever role runs it, and another role needs explicit grants on them.

## Azure OpenAI in Microsoft Foundry

Base: https://learn.microsoft.com/en-us/azure/foundry

- The v1 route is generally available. "`base_url` accepts both `https://YOUR-RESOURCE-NAME.openai.azure.com/openai/v1/` and `https://YOUR-RESOURCE-NAME.services.ai.azure.com/openai/v1/` formats." "`api-version` is no longer a required parameter with the v1 GA API." The client is the plain `OpenAI()`, and `model` is the deployment name. (openai/api-version-lifecycle)
- "For Azure OpenAI models we recommend using the Responses API". Chat Completions is supported for `gpt-5-mini` version 2025-08-07, with tools, parallel tool calls, structured outputs, system messages and streaming. Its context is 400,000 tokens, 272,000 of input and 128,000 of output. The GPT-5.6 models fail on Chat Completions with tools unless reasoning effort is `none`. (openai/api-version-lifecycle, openai/how-to/reasoning)
- "Reasoning models will only work with the `max_completion_tokens` parameter when using the Chat Completions API", and it covers reasoning tokens as well as the visible answer. They do not support `temperature`, `top_p`, `presence_penalty`, `frequency_penalty`, `logprobs`, `logit_bias` or `max_tokens`. `reasoning_effort` takes `low`, `medium` or `high`; `minimal` "works only with the original GPT-5 reasoning models", and the page does not name `gpt-5-mini` either way. (openai/how-to/reasoning)
- Tools are `{"type": "function", "function": {"name", "description", "parameters"}}`, with descriptions limited to 1,024 characters. `tool_choice` is `none`, `auto`, `required` or a named function. A tool call comes back in `choices[0].message.tool_calls[]` with `id`, `function.name` and `function.arguments` as a JSON string that "might not always be valid". A result goes back as a message with `role: "tool"` and `tool_call_id`. `finish_reason` is one of `stop`, `length`, `tool_calls`, `content_filter`. (openai/how-to/function-calling)
- Structured output is `response_format: {"type": "json_schema", "json_schema": {"name", "strict", "schema"}}`. Every property has to be required, objects need `additionalProperties: false`, and keywords such as `minLength`, `pattern`, `format`, `minimum` and `maxItems` are not supported. "Structured outputs are not supported with parallel function calls." (openai/how-to/structured-outputs)
- Usage: "Reasoning tokens never appear in the message content, but they occupy space in the context window and are billed as output tokens", and they are counted inside `completion_tokens`. "Cache hits show up as `cached_tokens` under `prompt_tokens_details`", inside `prompt_tokens`. Caching starts at 1,024 tokens of prompt. (openai/how-to/reasoning, openai/how-to/prompt-caching)
- A throttled call answers 429 with a `retry-after-ms` header. "Unsuccessful requests still count toward your per-minute rate limit." A prompt stopped by the content filter answers 400 with code `content_filter`; a filtered answer is a 200 with `finish_reason` `content_filter`. (openai/how-to/quota, foundry-models/concepts/content-filter)
- Global Standard prices per million tokens, from the Azure Retail Prices API: `gpt-5-mini` USD 0.25 input, 0.025 cached input and 2.00 output (meters "GPT 5 Mini Inpt Glbl", "GPT 5 Mini cchd Inpt Glbl" and "GPT 5 Mini outpt Glbl"); `gpt-4.1-mini` 0.40, 0.10 and 1.60, on meters priced per thousand; `text-embedding-3-small` 0.02. (https://prices.azure.com/api/retail/prices)
- Keyless access uses Entra ID with scope `https://ai.azure.com/.default`. The pages disagree on the role: the v1 page names Cognitive Services OpenAI User and the Foundry access page says to assign Foundry User and not the roles whose names start with Cognitive Services. Key authentication can be switched off with `disableLocalAuth`. (openai/api-version-lifecycle, concepts/rbac-foundry, https://learn.microsoft.com/en-us/azure/ai-services/disable-local-auth)
- Quota is assigned by tier. "Subscriptions in the Free tier (Tier 0) aren't eligible for quota increases." The page does not say which offer lands in which tier. (openai/quotas-limits)

## WhatsApp Cloud API

Base: https://developers.facebook.com/documentation/business-messaging/whatsapp

- Verification handshake is a GET with `hub.mode=subscribe`, `hub.challenge` and `hub.verify_token`; the endpoint answers 200 with the challenge. Each POST carries `X-Hub-Signature-256: sha256=<hash>`, an HMAC-SHA256 of the payload with the app secret as key. Mutual TLS is available per app. (webhooks/create-webhook-endpoint)
- Inbound messages are at `entry[].changes[].value.messages[]`. The message id is `messages[].id` (a `wamid.` string). The receiving number is `value.metadata.phone_number_id`, which is what I route tenants on. (webhooks/overview, webhooks/reference/messages/text)
- The customer has two identifiers: the phone (`from`, `contacts[].wa_id`) and a business-scoped user id (`from_user_id`, `contacts[].user_id`). Meta says to "build your integration to identify users by BSUID", because the phone is omitted once a user adopts a username. BSUIDs are scoped to a business portfolio and regenerated when the user changes phone number. Sending to a BSUID uses the `recipient` field. (webhooks/reference/messages, business-scoped-user-ids)
- Delivery: a failed webhook "is retried immediately, then a few more times with decreasing frequency over the next 7 days. Your server should handle deduplication". Notifications can be batched, up to 1,000 updates in one POST, and a payload can reach 3 MB. (webhooks/create-webhook-endpoint, webhooks/overview)
- Customer service window: 24 hours from the user's last message or call, reset by each new one. Outside it only approved templates can be sent; a free-form send fails with error 131047. (messages/send-messages, support/error-codes)
- Pricing changed on 2026-10-01: service messages are charged per message again. Each business phone number has 1,000 free service messages per month. The Brazil rate card effective 2026-10-01 lists BRL 0.035 (USD 0.0068) for service, utility and authentication and BRL 0.3217 for marketing. Without a payment method, service messages stop being delivered when the free tier is used up. (pricing)
- Sending: Graph API v27.0 (2026-11-04), `POST /v27.0/<PHONE_NUMBER_ID>/messages`. Marking as read and the typing indicator use the same endpoint; the indicator is dismissed after 25 seconds. Default throughput is 80 messages per second per number, and there is a limit of one message every 6 seconds to the same user (error 131056). (reference/whatsapp-business-phone-number/message-api, throughput)
- A new app gets a test account and a test phone number that need no payment method. A temporary token expires within hours; a system user token is long-lived. (about-the-platform, access-tokens)
- AI policy. The Meta Terms for WhatsApp Business Platform, section 4.7, last modified 2026-09-23, prohibit "AI Providers" from using the platform to offer AI technologies "when such technologies are the primary (rather than incidental or ancillary) functionality being made available for use, as determined by Meta in its sole discretion", and add that such technologies "may be made available to businesses in certain countries". The clause took effect on 2026-01-15. The pricing documentation says service messages "can be powered by a 3rd-party AI solution or people". For Brazilian numbers (+55), Meta's AI providers page says AI Providers can send service messages and are charged, effective 2026-03-11; this follows a preventive measure by CADE that its tribunal upheld on 2026-03-04. So the statement "WhatsApp forbids general-purpose assistants" is true as the general rule and not true for Brazil today. An agent closed to the tenant's own business is the ordinary case and pays ordinary service rates. (https://www.facebook.com/legal/Meta-Terms-for-WhatsApp-Business-Platform, pricing/ai-providers, https://www.gov.br/cade)
- Read again on 2026-11-18, before writing the adapter. An inbound text has the receiving number at `value.metadata.phone_number_id`; the customer's phone at `messages[].from` and `contacts[].wa_id`; the business-scoped user id at `messages[].from_user_id` and `contacts[].user_id`, in the form `US.13491208655302741918`; the profile name at `contacts[].profile.name`; `messages[].timestamp` as a string of Unix seconds; and the text at `messages[].text.body`. "`wa_id` and `from` are omitted when the user has adopted a username and their phone number is unavailable". (webhooks/reference/messages/text, webhooks/reference/messages)
- The answer to a send has the message id at `messages[0].id` and a `message_status` of `accepted`, `held_for_quality_assessment` or `paused`. An error has `error.code`, `error.message`, `error.type`, `error.error_data.details` and `error.fbtrace_id`. Code 131047 is the closed 24 hour window; 131056 is too many messages to one recipient, "Wait and retry the operation"; 130429 is the throughput limit, listed with 4 and 80007 as throttling; 131026 is an undeliverable recipient; 190 is an expired token. The page gives no HTTP status for them. (reference/whatsapp-business-phone-number/message-api, support/error-codes)
- A status update (`value.statuses[]`) carries the message id, the status, `recipient_id`, `recipient_user_id`, and a `pricing` object with `billable`, `pricing_model` and `category`. It carries no amount: what a message cost comes from the category and the rate card. "Businesses are only charged when a message is delivered", and "Each business phone number has one free tier of 1,000 delivered service messages per month". The two pages disagree on the value of `pricing_model` in their examples (`CBP` and `PMP`), so I do not read it. (webhooks/reference/messages, pricing)
- Addressing a send to a business-scoped user id uses `recipient` in place of `to`, with the whole id including its country prefix. The page still carries a sentence saying the APIs would not accept it "until July 2026". (business-scoped-user-ids)
- Automation rules: "You may use automation when responding during the 24-hour window, but must also have available prompt, clear, and direct escalation paths", and in-chat transfer to a human agent is one of the listed paths. Contacting someone requires their opt-in. (https://whatsappbusiness.com/policy/)

## MCP

- Official Python SDK: `mcp` 2.3.0 (2026-10-02); v2 is the stable line and v1 is in maintenance. The server class is `MCPServer` from `mcp.server`; the v1 import path `mcp.server.fastmcp` was removed. The standalone `fastmcp` package (4.2.0) is a separate project. (https://py.sdk.modelcontextprotocol.io/)

## Azure Service Bus

Base: https://learn.microsoft.com/en-us/azure/service-bus-messaging

- Sessions "provide concurrent demultiplexing of interleaved message streams while preserving and guaranteeing ordered delivery". "Only one receiver can have a lock on a session." The lock "is released when you call close methods on the receiver or when the lock expires". Sessions cannot be enabled or disabled after the queue is created, and a session queue takes no message without a session id. (message-sessions, enable-message-sessions)
- The lock duration is one minute by default and "The maximum value is 5 minutes, so you need to renew the lock if you want to have it longer". A lock "is volatile" and can be lost on a service update or a lost connection, in which case "the delivery count of the message isn't incremented". (message-transfers-locks-settlement)
- Duplicate detection: a message whose `MessageId` was seen in the window is accepted and "instantly ignored and dropped". The window "defaults to 10 minutes for queues and topics, with a minimum value of 20 seconds and a maximum value of 7 days". "Scheduled messages are included in duplicate detection." It cannot be enabled after creation. (duplicate-detection)
- Dead-lettering: the maximum delivery count "default value is 10. Whenever a message is delivered under a peek-lock, but is either explicitly abandoned or the lock has expired, the delivery count on the message is incremented". Past it the message moves to `<queue>/$deadletterqueue` "and the receiver continues receiving subsequent messages from the session". Closing a session with messages unsettled does not count a delivery. "Abandoning a message causes the same message to be served again by the next receive operation." (service-bus-dead-letter-queues, message-sessions)
- The Basic tier has neither sessions nor duplicate detection. Standard costs USD 0.013441 per hour with the first 13 million operations per month at no charge, the same in East US 2 and Brazil South. A message is at most 256 KB, and a message id and a session id at most 128 characters. (https://azure.microsoft.com/en-us/pricing/details/service-bus/, Retail Prices API, service-bus-quotas)
- With Entra ID the roles are Azure Service Bus Data Sender and Azure Service Bus Data Receiver, and an assignment can take up to five minutes to take effect. (service-bus-managed-service-identity)
- `azure-servicebus` 7.15.0 (2026-10-08). The async client is `azure.servicebus.aio.ServiceBusClient`, a session is accepted with `session_id=NEXT_AVAILABLE_SESSION`, and no free session within the wait raises `OperationTimeoutError`. The SDK does not guarantee that a client, sender or receiver is safe to share between coroutines. (https://pypi.org/pypi/azure-servicebus/json, https://github.com/Azure/azure-sdk-for-python/tree/main/sdk/servicebus/azure-servicebus)
- The emulator is `mcr.microsoft.com/azure-messaging/servicebus-emulator`, version 2.0.1, for amd64 and arm64. It needs a SQL Server container, listens on 5672 with a health endpoint on 5300, and accepts only a fixed connection string with `UseDevelopmentEmulator=true`. Queues come from a JSON file: creating entities through the administration client "is natively supported only in .NET". Its limits are one namespace, 50 entities, 10 concurrent connections, a maximum delivery count of 10, a duplicate window of five minutes at most and a lock of five minutes at most. Its licence allows use "to develop and test your applications". (overview-emulator, test-locally-with-service-bus-emulator, https://github.com/Azure/azure-service-bus-emulator-installer)
- Observed by running `azure-servicebus` 7.15.0 against the emulator 2.0.1 on 2026-11-17 (backend/tests/queue/test_contract.py holds the first six as tests). A held session is not given to a second receiver. Another session is. A duplicate message id is dropped. Closing a session without settling returns the message with the same delivery count, and abandoning adds one. After five abandons, the configured maximum, the message is no longer delivered. A message scheduled three seconds ahead on the session queue arrived on time. Each receiver is a connection of its own, so eight session receivers and a sender used nine of the ten the emulator allows. Accepting a session took about 0.46 s and closing it about 0.33 s. With client retries off, an accept with no session available returned one second after the wait asked for. Asking for more than one message made the receive wait a further 0.2 s after the first arrived. Two coroutines sending on one unopened sender failed with an error inside the SDK.

## PostgreSQL, RLS and pgvector

Base: https://www.postgresql.org/docs/current (PostgreSQL 18)

- PostgreSQL 18 is the current major. Azure Database for PostgreSQL flexible server offers 13 to 18; the minors it lists are 18.6 and 17.11. (https://www.postgresql.org/support/versioning/, https://learn.microsoft.com/en-us/azure/postgresql/configure-maintain/concepts-supported-versions)
- Superusers and roles with `BYPASSRLS` always bypass row security. Table owners bypass it unless the table has `FORCE ROW LEVEL SECURITY`. With RLS enabled and no policy, the default is deny. (ddl-rowsecurity.html)
- `USING` silently filters rows; `WITH CHECK` raises an error when the expression is false or null. (sql-createpolicy.html)
- Unique, primary key and foreign key checks bypass row security, which the docs call a possible covert channel: a failed insert tells the user the value exists. `TRUNCATE` and `REFERENCES` are not subject to row security. (ddl-rowsecurity.html, sql-createpolicy.html)
- `set_config(name, value, true)` applies only during the current transaction. A plain `SET` persists until the end of the session. `current_setting(name, true)` returns NULL for a setting that was never set instead of raising. (functions-admin.html, sql-set.html)
- SQLAlchemy's pool calls `rollback()` when a connection is returned and resets nothing else at session level. (https://docs.sqlalchemy.org/en/20/core/pooling.html)
- SQLAlchemy has no async event handlers; events are registered on the sync session class or `sync_engine`. `SessionEvents.after_begin` receives the connection and can run SQL on it. (https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html, https://docs.sqlalchemy.org/en/20/orm/events.html)
- `create_async_engine` with `postgresql+psycopg://` selects the async psycopg 3 dialect. The asyncpg dialect prepares every statement and needs extra configuration behind PgBouncer. (https://docs.sqlalchemy.org/en/20/dialects/postgresql.html)
- PgBouncer in transaction pooling never supports session `SET` or session advisory locks. (https://www.pgbouncer.org/features.html)
- pgvector: with approximate indexes "filtering is applied after the index is scanned", so a filtered query can return fewer rows than the limit. Iterative index scans exist since 0.8.0. For tenant isolation the README recommends list partitioning or separate tables, because a shared approximate index lets one tenant's vectors affect another's recall. HNSW indexes `vector` up to 2,000 dimensions. Latest release 0.8.7 (2026-10-01); flexible server ships 0.8.2 on PostgreSQL 18. (https://github.com/pgvector/pgvector, https://learn.microsoft.com/en-us/azure/postgresql/extensions/concepts-extensions-versions)
- Exclusion constraints on range types prevent overlap; `btree_gist` adds equality on scalar columns to the same constraint; a predicate makes the constraint partial. `btree_gist` is a trusted extension and is available on RDS for PostgreSQL 18. (rangetypes.html, sql-createtable.html, btree-gist.html)

## What the documentation did not settle

Each of these is either tested in the phase named or carried as a risk.

- LangGraph: what happens when a thread with a pending interrupt receives a new input instead of a resume. Not documented. The code never does it: a paused turn is only resumed, and a turn that starts over deletes its thread first (ADR 0002).
- LangGraph: whether a checkpoint written by one version of the graph can be resumed after a deploy that changed the graph. Matters for approvals that stay pending across a release. Phase 2.
- LangGraph checkpointer: no guidance on a custom schema, tenant isolation or RLS for its tables, and no documented pool settings.
- WhatsApp: whether the signature is computed over the exact raw bytes of the body. The docs say "the post body payload". Phase 5, against the real test number.
- WhatsApp: the body of a text send. The TextMessage schema of the reference page rendered empty when I read it on 2026-11-18, so the adapter uses the long-standing shape, `type` `text` with `text.body` and `text.preview_url`, unconfirmed on the current page. Phase 5, with the first real send.
- WhatsApp: whether a send addressed by `recipient` to a business-scoped user id is accepted today. Every customer of the test number has a phone, so the adapter addresses by phone when it has one. Not exercised.
- WhatsApp: any guarantee about the uniqueness scope of the message id, and about the order of inbound webhooks. I assume neither and order by provider timestamp, then by arrival.
- WhatsApp: any idempotency key for sending. I found none, so a crash between a successful send and recording it can produce one duplicate message. Documented as a residual risk.
- WhatsApp: the exact lifetime of the temporary token. The number of recipients is settled: the app console states that a test number can message up to 5 phone numbers, each verified by a code sent to it.
- WhatsApp: whether Meta could classify a vendor of multi-tenant business agents as an "AI Provider". The clause leaves it to Meta's discretion.
- WhatsApp: the outcome of the conciliation between CADE and Meta after April 2026, which decides whether the Brazil exception stays.
- PostgreSQL: whether a custom setting returns NULL or an empty string after a transaction-local `set_config` ends. The policy handles both; Phase 1 has the test.
- OpenTelemetry: no date for the GenAI conventions to become stable.
- Azure OpenAI: whether `reasoning_effort` `minimal` is accepted by `gpt-5-mini`, and whether `verbosity` is accepted on Chat Completions. I use `low` and do not send `verbosity`.
- Azure OpenAI: any service-side timeout of a request on Global Standard, and the body of a 429.
- Azure for Students: its vCPU and Container Apps quotas, whether the twelve-month free PostgreSQL applies to it, and which quota tier it is. The regions are settled above. Phase 5.
- Service Bus: whether the queue's lock duration is also the session's, and any ordering promise for a scheduled message inside a session.
- Service Bus emulator: no statement of which features it supports beyond the configuration keys. What I rely on is tested.
- Container Apps: whether a response that keeps sending data, such as an event stream, is cut at the 240 second request timeout.
- Container Apps: whether the queue-length scaler counts messages in locked sessions, and which Service Bus role its identity needs.
- Container Apps: whether images can be pulled from a public GitHub Container Registry with no registry of my own. The page says "any public or private container registry" and does not name it.
- PostgreSQL flexible server: whether public and private access can be switched after creation.
